# chat-questioner 设计方案 —— 对话期游戏设计知识库（RAG）

## 1. 背景与目标

### 1.1 问题
NewBee 每轮协议 [F2] 的第 2 步"动态投喂 2 个定制创意"完全靠 LLM 现场编造。这带来两类隐患：

- **泛泛与套路化**：缺乏真实参考接地，例子容易空洞、似是而非。
- **幻觉与不可落地**：可能编出不存在的参考游戏，或给出小团队做不出来的机制，违背 MVP 纪律。

### 1.2 目标
给对话期引入一个**游戏设计知识库**，在每轮按当前对话状态**检索**真实、结构化的设计参考（标杆游戏 / 机制 / 情绪锚点 / juice / 循环 pattern），注入提示词供"动态投喂"借鉴改编。直接服务价值线 1（做出好游戏），并因知识 tag 对齐 DSL 词汇，**副作用**是产出的 `intentTerms/signatureTerms` 更易命中 resolver 选型。

### 1.3 非目标
- **不碰 resolver 选型期**：选型仍是确定性、无损、agent 不介入的映射。对话期 RAG 的"模糊召回"只影响创意发散，与选型期的确定性是两个世界。
- 不引入云端向量服务、不引入鉴权/多用户/云持久化（延续 §1.3 主设计边界）。

## 2. 关键决策记录

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| K1 | 接入时间窗 | **对话期**（NewBee 投喂接地） | 改动全落在 chat-questioner，不动 agentic_os，ROI 最高 |
| K2 | 运行时机制 | **按需检索注入（RAG）** | 小白大白话场景，需贴题材召回；静态注入装不下长尾题材 |
| K3 | 知识来源 | **目录种子 + 人工精修** | 复用 resolver 适配器抽种子，与 resolver 同一套词汇宇宙 |
| K4 | 检索技术 | **混合：结构化预筛 + 向量排序** | 预筛守"阶段机/单步"纪律，向量解大白话召回 |
| K5 | embedding 提供方 | **本地模型（transformers.js + 中文小模型）** | 预检确认代理无 embedding（见 §3）；本地离线免费，契合无云持久化边界 |

### 预检结论（2026-06-04）
对 `https://llm-proxy.forgeax.com/v1` 实测：

- `/v1/models` 列出的全是对话/图像/视频模型，**无任何 embedding 模型**。
- 直接打 `/v1/embeddings` 试 `text-embedding-3-small` / `text-embedding-004` / `gemini-embedding-001` / `qwen-embedding` / `bge-m3` / `embedding-3`，**全部被拒**（`Invalid model name`）。

→ 复用代理做向量不可行，故 K5 选**本地 embedding 模型**。

## 3. 总体架构

新增单一职责包 `packages/knowledge`，依赖方向延续主设计的单向规则（避免环）：

```text
conversation → knowledge → dsl(仅类型)
server → knowledge          # 装配检索器 + 构建期生成索引
```

`knowledge` 只做三件事：**定义知识卡 schema** / **构建 `knowledge-index.json`（种子 + 精修 + 烘焙向量）** / **提供 `retrieve(state, query)` 检索器**。它不依赖 `conversation`；由 `conversation` 反向接收一个**可选** retriever 依赖（缺省时行为与现状完全一致，向后兼容）。

```text
chat-questioner/
└── packages/
    └── knowledge/
        ├── src/
        │   ├── card.ts          # 知识卡 schema（zod + TS 类型）
        │   ├── embed.ts         # 本地 embedding 封装（transformers.js）
        │   ├── seed.ts          # 从 buildCatalog() 抽种子 → 卡
        │   ├── build.ts         # 种子 + 精修 + 烘向量 → knowledge-index.json
        │   ├── retrieve.ts      # 混合检索器：预筛 + 向量排序
        │   └── index.ts
        ├── data/                # 人工/LLM 精修卡（*.yaml）
        ├── scripts/build-knowledge.ts
        └── knowledge-index.json # 构建期产物（可选提交快照）
```

## 4. 知识卡 schema（对齐 DSL/state 词汇）

```jsonc
{
  "id": "ref-stardew-valley",
  "type": "reference-game",        // reference-game | mechanic | emotion-anchor | juice | loop-pattern
  "title": "星露谷物语",
  "body": "治愈系农场经营，核心爽点是'缓慢积累 + 自由节奏'……（喂给 LLM 的接地素材）",
  "tags": {
    "genre": ["farming-sim"],       // 对齐 engineering.genre
    "mechanics": ["collect", "upgrade"],
    "modalities": ["audio"],
    "emotion": ["治愈", "解压"],     // 对齐 coreEmotion（大白话）
    "artStyle": ["pixel-cozy"]
  },
  "stageAffinity": [1, 2],          // 适合在哪些阶段被投喂
  "embedding": [/* 构建期烘入，运行时直接读 */]
}
```

- schema 用 zod 定义 + 导出 TS 类型；`tags` 的取值刻意落在 `ConversationState.engineering` 与 DSL 受控词汇上，保证对话期投喂能顺流到选型期。
- `embedding` 仅出现在构建期产物里；检索器返回给提示词的对象**剔除 `embedding`/`tags` 等内部字段**，只给 `title + body`。

## 5. 索引构建（构建期生成，对齐主设计 D8）

新增 `pnpm build:knowledge`，产出 `knowledge-index.json`：

1. **种子（`seed.ts`）**：调 `buildCatalog(FORGEAX_ROOT)` → 把 `TemplateEntry` 转 `reference-game`/`mechanic` 卡（`desc`→`body`，`intentTerms`/`signatureTerms`/genre→`tags`）；narrative specialist、art tags 转对应卡。
2. **精修（`data/*.yaml`）**：人工或 LLM 辅助写的标杆卡、情绪锚点卡、juice/循环 pattern 卡，合并进来。
3. **烘焙向量（`embed.ts`）**：对每张卡的 `title + body + 扁平化 tags` 用**本地 embedding 模型**算一次向量写入 `embedding`。运行时因此**零模型推理开销于卡侧**，仅对用户 query 算一次；也保证离线/CI 可复现。

> `build:knowledge` 依赖 `build:catalog` 同源，杜绝 KB 与 catalog 漂移。可选提交一份 `knowledge-index.json` 快照作离线/CI 兜底。

---

## 6. 检索器（混合：结构化预筛 + 向量排序）

`retrieve(state: ConversationState, query: string, k = 3): Promise<RetrievedCard[]>`：

1. **预筛（守阶段机/单步纪律）**：按 `state.stage` 映射到该投喂的 `type` 集合，再按 `state.engineering.{genre,modalities,artStyle}` 与 `coreEmotion` 做 tag 软过滤，把候选缩到几十张。

   | 阶段 | 召回的卡 type |
   |---|---|
   | 1 火花 | reference-game |
   | 2 核心体验/四元素 | emotion-anchor, reference-game |
   | 3 核心循环 | loop-pattern, mechanic |
   | 4 美学/juice | juice |
   | 5 世界叙事 | reference-game（叙事向） |
   | 6 平衡心流 | loop-pattern, mechanic |

2. **向量排序（解大白话）**：把"用户最近一句 + 关键 state 信号（coreEmotion/genre）"拼成短 query，本地算 embedding，在候选集上算 cosine，取 top-k。语料小，**内存暴力点积即可，先不引入 hnswlib**。
3. 返回 top-k 的 `{ title, body }`（剔除内部字段）。

> 预筛为空（如阶段 0）或无命中：返回空数组，投喂回退为纯现编——降级安全。

## 7. 接入 `advance()`（最小改动）

`packages/conversation/src/advance.ts` 的 `AdvanceDeps` 增可选项：

```ts
export interface AdvanceDeps {
  llm: LlmClient;
  systemPrompt: string;
  onToken?: (token: string) => void;
  retrieve?: (state: ConversationState, query: string) => Promise<RetrievedCard[]>; // 新增，可选
}
```

在拼 `messages` 前插一步：若有 `retrieve`，用它拿卡 → 组装 `KNOWLEDGE_CONTEXT` fragment 追加到 system 末尾：

```text
[F2 投喂素材] 以下是与当前题材相关的真实设计参考，**仅供你第 2 步"动态投喂"借鉴改编**，
不要直接照搬、不要向用户暴露这些条目本身：
- 《星露谷》：缓慢积累 + 自由节奏的治愈感……
- 机制·连接消除：……
```

`messages = [{ system: systemPrompt + TURN_DIRECTIVE + KNOWLEDGE_CONTEXT }, ...history]`。`retrieve` 缺省 → 与现状逐字节一致。

**提示词侧**：`newbee.system.md` 补一小段 `[F2.5]`，要求投喂的 2 个创意**优先从提供的参考取材/改编**，无相关参考时才纯现编，且**永不暴露卡片元数据**。（profile 化后 v3/v4 同样受益，因 `[F2.5]` 属共享 fragment。）

## 8. embedding 客户端与配置

- `packages/knowledge/src/embed.ts`：封装 transformers.js（`@huggingface/transformers`），默认中文小模型（候选：`bge-small-zh-v1.5` / `multilingual-e5-small`）。单例懒加载，进程内复用。
- 新增依赖：`@huggingface/transformers`。首次运行下载权重（约 30–100MB），缓存本地。
- config（`apps/server/src/config.ts`）增：

```bash
KB_EMBEDDING_MODEL=Xenova/bge-small-zh-v1.5   # 本地模型 id
KB_TOP_K=3
```

- `apps/server/src/main.ts`：`buildCatalog` 后加载 `knowledge-index.json`，装配 retriever 注入 `advance` 的 deps（沿用 profile 化后的 wire 路径）。

## 9. 错误处理

| 场景 | 处理 |
|---|---|
| `knowledge-index.json` 缺失/损坏 | server 启动告警，retriever 置空 → 投喂回退纯现编，不阻塞对话 |
| 本地模型下载失败/首载慢 | 启动期预热一次；失败则 retriever 降级为关键词排序（预筛不变） |
| query embedding 超时 | 设超时；超时回退该轮不注入知识，照常投喂 |
| 预筛/向量均无命中 | 返回空，正常对话 |
| KB 与 catalog 漂移 | `build:knowledge` 依赖 `build:catalog`，构建期同源 |

## 10. 测试策略

- **检索器单测**：预筛映射正确性（阶段→type）、tag 过滤、cosine 排序；注入假向量做确定性断言。
- **索引构建 golden**：对真实 forgeax 目录跑 `seed.ts`，断言卡数量/字段映射。
- **conversation 剧本回放扩展**：喂罐装答案 + 假 retriever，断言 ① 知识卡被注入 system；② `reply` 不泄露卡元数据；③ 阶段推进、`ConversationState`、最终 DSL 与无 KB 时收敛口径一致。
- **embed 冒烟**：本地模型对中英文短文本产出固定维度向量。

## 11. 里程碑（建议交付顺序，全程 TDD）

1. **K-M0 · 卡 schema + 检索器骨架**：`card.ts`（zod）+ `retrieve.ts`（预筛 + 可注入排序器）+ 单测（假向量）。← 先锁接口，不依赖模型。
2. **K-M1 · 种子 + 构建**：`seed.ts`（复用 `buildCatalog`）+ `build.ts` + `embed.ts`（本地模型）+ `build:knowledge` + golden。
3. **K-M2 · 接线 `advance` + 提示词**：`AdvanceDeps.retrieve` + `KNOWLEDGE_CONTEXT` 组装 + `[F2.5]` fragment + 回放测试。
4. **K-M3 · server 装配**：`config` 增项 + `main.ts` 加载索引/装配 retriever + SSE 端到端冒烟。
5. **K-M4（可选）· 精修扩库**：补标杆/情绪/juice 卡，提升投喂质量。

> K-M0+K-M1 完成即可离线验证"检索能否召回贴题材的真实参考"这一最硬假设，不依赖 UI。
